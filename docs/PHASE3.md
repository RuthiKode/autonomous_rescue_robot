# Phase 3 report: Nav2 on live SLAM (plan week 4)

Run on 2026-11-19 and 2026-11-20, same machine and stack as Phase 2 (Ubuntu 24.04 under WSL2, ROS 2 Jazzy, Gazebo Harmonic, RTX 4050), `wheel_mu` 0.12.

**Result.** Nav2 plans and drives on slam_toolbox's live map, a hazard layer publishes `/hazard_map`, and a goal runner scores random reachable goals. Goal success over 3 runs of 20 goals per world is **100% in collapsed and open_plan and 55% in rooms** (runs of 60%, 95% and 10%). The rooms failures come from slam_toolbox's pose estimate jumping by 1.0-1.6 m during navigation, after which every plan fails; I could not fix that in this phase (see "Known issues"). No goal ended stuck without a recovery in the final baseline. Not checked by eye: RViz2 and the Gazebo GUI.

## What was built

### Nav2 on slam_toolbox's live map (`rescue_navigation`)

```bash
ros2 launch rescue_bringup navigation_sim.launch.py world:=rooms headless:=true
# or in two steps, as run_eval does:
ros2 launch rescue_bringup mapping.launch.py world:=rooms headless:=true
ros2 launch rescue_navigation navigation.launch.py
```

`navigation.launch.py` includes Nav2's own `navigation_launch.py` only: no map server, no AMCL. slam_toolbox publishes `/map` and `map -> odom`; the EKF publishes `odom -> base_link`. With the stack up, `ros2 lifecycle get` shows every Nav2 server `active`, and the velocity chain is controller (`/cmd_vel_nav`) to velocity smoother (`/cmd_vel_smoothed`) to collision monitor (`/cmd_vel`). The TF test confirms one publisher per transform with Nav2 running.

The parameters are Nav2 Jazzy's default file with 17 listed changes, generated by `scripts/make_nav_params.py` (every change must match the default exactly, so a Nav2 update fails loudly). The header of `rescue_navigation/config/nav2_params.yaml` lists them. In groups:

- **Topics and frames:** EKF output as the odometry source in the BT navigator, the controller server and the velocity smoother; the collision monitor uses `base_link` (this robot has no `base_footprint`).
- **Controller limits:** forward speed 0.4 m/s (robot maximum 0.6), reverse 0.2, turn rate 1.5 rad/s, accelerations 1.5 m/s^2 and 4.0 rad/s^2, which are the robot's own limits (a unit test checks them against the Xacro).
- **Footprint:** the real 0.40 x 0.28 m rectangle in both costmaps instead of Nav2's 0.22 m circle, and MPPI's cost critic checks it (`consider_footprint`). The log had warned that the costmaps and the critic disagreed about the robot's shape.
- **Inflation:** radius 0.45 m, the footprint's circumscribed radius (0.30 m) plus a 0.15 m margin; Nav2's default 0.70 m would swallow the 0.7 m gaps.
- **Depth camera as a second obstacle source:** see below.

Recoveries are Nav2's defaults: clear costmaps, spin, wait and back-up in a round-robin after a planner or controller failure.

**Bug found and fixed: the controller's odometry topic.** The controller server reads its current speed from `/odom` by default. This robot has no `/odom`, so MPPI believed the robot was always at rest and could only add one control step of speed (1.5 m/s^2 x 0.05 s). The first diagnostic showed the controller commanding 0.06-0.07 m/s however far the goal was, and a 6 m path took 116 s with 15 "failed to make progress" aborts. I had set the odometry topic in two other places and missed this one. With `odom_topic: /odometry/filtered` in the controller server the same robot commands the full 0.40 m/s and a 3 m goal takes about 7 s. A unit test now checks the setting.

### Depth camera for low obstacles

The 2D LiDAR plane is at 0.20 m, so a lying survivor's legs are invisible to it (the plan's own note). In the first collapsed-world baseline (LiDAR only) the robot was pinned against survivor 3's feet for the last three goals: wheels spinning, MPPI commanding 0.1-0.3 m/s, the robot's true position unchanged for over 300 s, and no recovery ever firing, because wheel odometry said the robot was moving and Nav2's progress check saw progress. Fix: the depth image is resized to half size (nearest neighbour, so depth is not averaged across edges), converted to a point cloud (`depth_image_proc`, one component container with in-process transport), and used as a second observation source (0.04-0.60 m above the floor, 0.3-2.0 m ahead) in voxel layers in both costmaps. Voxel layers are needed because a plain obstacle layer lets a LiDAR ray at 0.20 m erase the low marks the camera made.

| | Measured |
| --- | --- |
| `/camera/depth/points` | 14.95 Hz in sim time, 1.3% of frames dropped, 76,800 points per frame |
| Full-size cloud (rejected) | 307,200 points per frame; about 0.8 Hz reached a monitor |
| Real-time factor during goals (180 goals) | min 0.67, mean 0.85, max 0.91 |
| The goal that pinned the robot, afterwards | succeeded in 22.5 s, 6.2 m |

### Hazard layer (`rescue_mapping`)

```bash
ros2 run rescue_mapping hazard_layer --ros-args -p config_file:=src/rescue_mapping/config/hazard.yaml
```

(it starts with `navigation.launch.py`; `hazard:=false` turns it off). It subscribes to `/map` and publishes `/hazard_map` on the same grid (transient local): 100 for a known-free cell in a passage narrower than the robot's width plus a margin, 0 for other known-free cells, -1 for occupied and unknown.

**Definition.** The width is the robot's swept width, because it can turn in place: the diameter of the circle through its farthest corner, 2 x 0.295 = 0.59 m (a test checks this against the Xacro), plus a 0.20 m margin: 0.79 m. That makes the collapsed world's 0.7 m gaps hazards and the rooms world's 1.0 m doors not.

**Method.** Distance to the nearest obstacle at every cell (unknown counts as free, so a half-explored corridor is not called narrow); the ridge of that distance (the medial axis); ridge pieces narrower than the threshold that touch the wide ridge in two or more separate places, i.e. necks linking two wide regions; the union of the maximal disks along them; regions under 0.08 m^2 dropped. **A plain morphological opening was tried first and rejected:** a disk of the passage width reaches into a short gap from both sides and covers it, so 0.7 m gaps in a thin barrier were missed. I noticed this while reasoning about the opening, before it ran on a real map.

**Checks.** 11 unit tests on synthetic maps with known widths: gaps of 0.7 m are hazards, gaps of 0.9, 1.0 and 1.5 m are not, empty rooms (corners included) have none, a 0.5 m corridor is a hazard and a 2 m one is not, a gap is still found when the rooms are joined elsewhere, unknown cells are never hazards. On the real maps (ground-truth grids and saved SLAM maps, rendered and looked at):

| World | Truth grid | SLAM map (slip run, seed 1) | What the regions are |
| --- | --- | --- | --- |
| collapsed | 10 regions | 9 regions | the four 0.7 m gaps at (0.0, 2.0), (-4.6, 2.0), (2.5, 4.4), (2.5, -1.7) plus debris clusters; the SLAM map shows the three gaps the start-zone drive can see |
| rooms | 11 regions | 13 regions | tight spots between furniture and walls; the 1.0 m doors are not marked |
| open_plan | 6 regions | 10 regions | tight spots between clutter and pillars |

The layer runs live (it published `/hazard_map` of 280 cells wide in the collapsed run), but I did not look at it live in RViz2, and nothing consumes it yet: the plan uses it as a cost penalty for exploration (Phase 6). Ridge points narrower than 0.28 m are ignored, since the robot cannot enter them at all and the costmap already blocks them. Dead-end narrow alcoves are not reported, only passages between two wide regions.

### Goal runner (`rescue_eval nav_goals`, `run_eval --nav-goals`)

```bash
# whole run: simulation + SLAM, warm-up replay, Nav2, 20 goals, scored into the CSV
ros2 run rescue_eval run_eval --world rooms --seed 1 --slam --drive src/rescue_eval/drives/rooms.csv \
    --nav-goals 20 --nav-seed 1 --method nav_baseline --output-dir results/phase3
# explicit goals against a running stack
ros2 run rescue_eval nav_goals --world collapsed --goal=5.0,-1.5 --goal=1.0,-1.0
```

- **Warm-up first.** The simulation and SLAM start, the recorded drive for that world is replayed so SLAM has a map, and only then does Nav2 start. Nav2 running during the replay disturbs it: its collision monitor and velocity smoother also publish on `/cmd_vel`, and my first test suggested the replayed robot never completed its tour (the planner reported it far from where the replay should have left it).
- **Goal selection.** Goals are drawn once, after the warm-up, from a seeded generator. A cell qualifies if it is reachable from the spawn on the generator's own geometry (the ground truth, at 0.45 m clearance) and its 0.35 m disk is known-free in the live SLAM map. Consecutive goals are at least 1.5 m apart and goals at least 1.0 m apart. Ground truth is used only to choose and to score; Nav2 never sees it.
- **Success.** Nav2 reports `SUCCEEDED` and Gazebo's true pose ends within 0.35 m of the goal. A 120 s sim-time limit cancels a goal.
- **Per goal** (`runs/<run_id>/goals.csv`): goal and start, status, Nav2 error code, sim and wall time, true path length, true final error, the recoveries Nav2 reports in its feedback, and the recoveries seen on `/behavior_tree_log`.
- **Recovery logging.** Every time `Spin`, `Wait`, `BackUp`, `DriveOnHeading` or a clear-costmap node of the behavior tree goes to `RUNNING`, the runner logs `recovery fired: <name>` and records it in the goal's row. Nav2's own counter and the logged events differ (Nav2 counts retry loops that are not named nodes); both are kept.
- **Stuck.** A goal that ran to its time limit with no recovery ever firing is flagged `stuck_without_recovery`. A goal that Nav2 aborted with an error is a reported failure and is not flagged.
- **Nav2 start-up retry.** Once, Nav2's lifecycle manager aborted its whole bring-up because one transform lookup timed out in the first half second (`base_link` to `odom`), and the run ended `nav_not_active`. `run_eval` now restarts Nav2 up to three times. That one run was repeated; the failed row stays in the CSV.

### Unreachable goal

A goal outside the map (11.0, 0.0) in the rooms world is rejected by the planner at once ("goal outside bounds", 0.1 s) and never reaches the recovery logic; the next goal then succeeded. That is the correct behaviour but not a test of recoveries. Recoveries were exercised by real failures instead: in the three rooms runs Nav2 started its round-robin (spin, wait, back-up, spin) after planner failures and the runner logged each one.

## Known issues

- **slam_toolbox's pose jumps 1.0-1.6 m in the rooms world, and navigation does not recover.** In two of three rooms runs of the final baseline the map-frame pose of `base_link` was 0.01-0.03 m from Gazebo truth until it suddenly was 1.0-1.5 m away (rooms seed 3 at goal 3: 1.01 m; seed 1 at goal 9: 1.46 m) and stayed there. Nav2 then plans from the wrong pose, which lies inside walls in its own costmap (cost 97 at the robot, half of the surrounding cells lethal), so every later goal aborts with "no valid path" while the recovery behaviours fire without effect. The other worlds never showed it in 6 runs (120 goals). Evidence about the cause:
  - It is intermittent. The goal list that contains (0.72, -4.47) as goal 9 failed at that goal in four separate runs, all with the depth source on. That same goal sent alone after the same warm-up succeeded, with the depth source on and off. Rooms seed 3 failed at goal 3 in the baseline and succeeded at goal 3 when rerun unchanged.
  - **Stricter loop-closure acceptance did not help.** I raised the response thresholds (coarse 0.35 to 0.55, fine 0.45 to 0.65) and tightened the variance limit (3.0 to 1.5). A 12-goal run was clean, but a full 20-goal run failed at goal 9 again with the same 1.46 m jump near (1.1, -2.8). I reverted the change; those results are in `results/phase3_experiment_strict_loop_closure/`.
  - **Whether the depth source plays a part is not settled.** Every rooms failure so far (five runs) had it on, and the two rooms runs with it off were clean (30 goals), but those drew different goal lists, there are only two of them, and the depth source cannot touch SLAM except through CPU load and timing. The single-goal test gave identical results with it on and off (22.6 s, 5.9 m path).
  - **My best remaining guess, untested:** scan matching in a feature-poor corridor (it is degenerate along the corridor axis) under wheel slip (`wheel_mu` 0.12), combined with the four near-identical rooms per side. The plan already puts this failure in the mission tree ("localization jump: map-to-odom changes by more than a threshold in one step", stage 7), which is where a response belongs.
- **Nav2's progress check cannot see a robot that is pinned with spinning wheels**, because it uses the odometry pose. Depth obstacles remove the one cause seen so far, but any other low or unseen obstacle would repeat it.
- **The hazard layer is not used yet** (exploration, Phase 6) and was not looked at in RViz2.
- **Goal sampling is sensitive to the live map**: tiny map differences change the goal list after a few goals, so two runs with the same seed can differ.
- **The unreachable-goal check is weak** (outside the map only).
- **MPPI is heavy**: the real-time factor during goals was 0.67-0.91 (mean 0.85), compared with about 1.0 without Nav2.
- **Phase 2's mapping baseline** was measured without Nav2 and is unchanged; the maps scored inside the Phase 3 runs are the same warm-up replays.
- **Carried over:** nobody has looked at RViz2 or the Gazebo GUI; `results/` is not committed.

## Deviations from the plan and from the Phase 3 instruction

- **Real footprint instead of a robot radius**, and MPPI's footprint check on: needed for a 0.40 x 0.28 m robot in 0.7 m gaps. The plan said to change only the inflation radius and the controller limits; the other changes in the parameter header were each needed (odometry topics, the collision-monitor frame, the depth source).
- **Depth camera feeds the costmaps**, and `depth_image_proc` / `image_proc` are new dependencies. The plan gives the depth image a job in survivor localization only.
- **Nav2 starts after the warm-up replay** and is restarted if its bring-up aborts.
- **Goals are drawn from ground truth reachability filtered by the live map**, and scored with the true pose; one run is 20 goals, three runs per world.
- **Hazard threshold uses the swept width (0.59 m) plus 0.20 m**, not the 0.28 m chassis width.
- **Collapsed goals are in the start zone** in the random-goal baseline; the gaps have their own test.
- **Recovery logging comes from `/behavior_tree_log`**, not from Nav2's own counter, which is also recorded.

## Decision

**Settled: leave the rooms SLAM jump for the mission tree.** The localization-jump branch (plan stage 7: map-to-odom changes by more than a threshold in one step, then stop, rotate in place to re-scan, resume) is where the response belongs. The rooms numbers above stay as measured, with no fix attempted. I added the risk to the plan's risks table (`docs/PLAN.md`). Open for that phase: whether the depth source plays a part (rooms with it off, many seeds), and whether stopping and re-scanning actually re-localizes a pose that is 1-1.5 m off, since SLAM here never corrected itself.
